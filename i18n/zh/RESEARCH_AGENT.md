# 代理程序：如何在没有 AI 助手的情况下帮助项目

[English](../../docs/RESEARCH_AGENT.en.md) · **中文** · [Español](../es/RESEARCH_AGENT.md) · [Français](../fr/RESEARCH_AGENT.md) · [Deutsch](../de/RESEARCH_AGENT.md) · [Italiano](../it/RESEARCH_AGENT.md) · [Русский](../../docs/RESEARCH_AGENT.md) · [Português](../pt/RESEARCH_AGENT.md) · [العربية](../ar/RESEARCH_AGENT.md)

截至 2026 年 11 月 22 日的状态。代理程序版本 0.2.0（准备发布）。面向参与者的说明：
[agent/README.md](../../agent/README.md)（[俄文版](../ru/AGENT.md)）。

## 为什么

本仓库面向拥有 AI 助手的人：AI 助手阅读文档并帮助设计。大多数人没有这样的助手，但有电脑或手机。
代理程序给他们一种参与方式：它定期查看本仓库，领取任务，在参与者的设备上执行这些任务并发布结果。

在此阶段**不提供任何奖励**：没有积分，没有金钱，也没有对未来报酬的承诺。
目标是把尽可能多的计算资源和独立验证者吸引到架构设计中来。

代理程序是**研究工具，而不是 SkyNet 网络**。它比网络应当具备的形式更简单、更中心化，
并且它自身并不满足网络的强制要求。下文在每一处都直接说明了这一点。

## 它是如何构成的

| 部分 | 存放位置 | 做什么 |
|---|---|---|
| 任务列表 | `tasks/index.json` 及签名 `tasks/index.json.sig` | 指定内置计算、其参数和独立分片的数量 |
| 代理程序 | `agent/skynet_agent/`，仅使用 Python 3.9+ 的标准库 | 校验签名、选择分片、计算、发布、更新 |
| 版本说明 | `agent/release.json` 及签名 | 列出代理程序文件及其大小和 SHA-256 |
| 启动器 | `agent/launcher.py` | 启动当前版本，切换到新版本，并在版本损坏时回滚 |
| 结果 | 由设备密钥签名、经公开的 Nostr 中继器和完整节点发布的记录（[任务看板](BOARD.md)）；可选——GitHub 任务中的评论 | 带结果指纹的机器可读记录 |
| 汇总 | `results/`，由 `tools/collect_results.py` 构建 | 比对不同人的结果，复核发现 |

代理程序的一个工作循环：

1. 每 30 分钟一次（带随机偏移）下载版本说明和任务列表。
2. 用内置在已安装副本中的发布密钥校验其中每一个的签名。
3. 如果存在编号更大的版本，就下载它的文件，将每个文件与指纹比对，
   放到当前版本旁边并重新启动。
4. 随机选择一个尚未计算过的任务分片。
5. 在单独的进程中以最低优先级并在时间限制下计算它。
6. 把结果放入“发件箱”，并以本设备密钥签名的记录发送，立即发往多个公开的 Nostr 中继器和
   完整节点。无需账户。当两个中继器或一个节点确认了该记录时，即视为已送达；否则它留在
   “发件箱”中，并重试：一分钟后，然后间隔加倍，但不超过一小时。重试发送同一条记录，
   因此结果不会被重复计入。旧方式——以参与者名义在 GitHub 任务中发布评论——通过设置
   `submit_via github` 开启。积累三百个未发送的结果后，代理程序停止接取工作并就此报告。

没有调度器：每个代理程序自行选择分片。不同参与者选择相同分片是刻意设计的：
所有计算任务都是整数计算，因此在任何设备上都会得到相同的数字。不同 GitHub 账户之间的
指纹一致被视为确认；不同密钥之间的一致则不算，因为密钥没有任何成本，一个人可以创建
任意多个密钥。此类分片由重算确认。

## 任务是数据，而不是程序

代理程序从不下载或运行来自任务的代码。任务指定内置于代理程序中的一种计算
（“内核”），并把数字传递给它。每个内核都会校验参数并限制工作量。新的计算类型
只会随代理程序新的已签名版本出现，其源代码存放在仓库中并可人工阅读。

0.1 版内核：

| 内核 | 计算内容 |
|---|---|
| `selftest` | 对照性的整数计算：指纹必须在所有设备上一致 |
| `exit-scam-a` | 对即将离开前提交伪造结果的参与者的支付期望的精确计算（[CURRENT_DESIGN](CURRENT_DESIGN.md) 中的方案 A）；枚举一族策略并报告那些比诚实离开更有利的策略 |
| `lottery-b` | 若只对已验证任务付款，出现亏损月份或季度的精确概率（方案 B） |
| `ai-answer` | 依参与者意愿：向由他自行运行的本地 AI 模型提问 |

每次计算的精确模型都写在相应内核源文件的开头，以便任何人都能独立重算结果。
任务及其含义：[tasks/README.md](../../tasks/README.md)。

**与项目关于实验的规则的边界。** 首批任务是根据文档中的公式进行的计算
（成本分析和寻找反例）以及向语言模型提出的问题。它们不是在设备上的测量，
也不是针对网络的实验。测量类任务（例如，不同显卡上整数输出的比特是否一致）
只有在项目所有者决定开展实验后才会发布。

## AI 模式（可选，实验性）

在自己设备上运行开放模型（Ollama、llama.cpp 服务器、LM Studio 以及具有与
OpenAI 兼容接口的类似工具）的参与者，可以启用 `ai.enabled`。此后代理程序会把
来自已签名列表的问题交给模型并发布回答。这样，没有 AI 订阅但有显卡的人就成为
了“模型委员会”的参与者。

- 代理程序不会下载或启动模型，并且默认只访问同一台电脑上的服务器。
- 问题及其引用的文档由已签名的列表指定。每份文档都会与指纹比对，
  因此无法把别的文本塞给模型。
- 回答默认在“发件箱”中等待，直到参与者批准：文本以他的名义发布。
- 回答会被标记为机器生成且未经任何人验证。每个问题的回答数量有限制。

仅在自动化测试中的替身服务器上验证过。该模式尚未用真实的模型运行环境验证过。

## Android 应用（实验性）

对于不想配置 Termux 的人，有一个应用：一个 APK 文件，一个“Start”按钮。
源代码和说明：[android/README.md](ANDROID.md)。应用中内置了同一个
`skynet_agent` 包和 Python（通过 Chaquopy）。与电脑上的代理程序的差异：

- Android 不允许运行单独的 Python 进程，因此分片在应用自身的后台进程中
  逐个计算。如果分片超过时限，看门程序会结束该进程，Android 会重新启动服务，
  而该任务留给更快的设备。
- 代理程序的新版本从仓库获取，并使用相同的发布密钥签名。内置副本负责校验它；
  如果新版本在这里无法启动或其文件被改动，应用会回退到内置版本。
- 应用本身（界面、服务、看门程序）只能通过新的 APK 更新。APK 用项目维护者的
  另一个密钥签名：这是网络中不应存在的第二个单一信任点。
- 结果以签名记录的形式发出，与电脑上的代理程序相同。只有在参与者选择了旧的
  发布方式时，才需要 GitHub 令牌。
- 除非参与者另行允许，否则仅在充电时工作。没有 AI 模式。

截至 2026 年 11 月 22 日的状态：应用可以构建，其 Python 部分在电脑上通过了
测试（`agent/tests/test_android_glue.py`）。使用测试密钥的验证构建在
Android 14（x86_64）模拟器上配合本地测试仓库通过：安装、签名校验、无误地计算
全部 7 个测试分片、未充电时的等待、后台运行、保存令牌并用它访问真正的
GitHub API、停止并在保留状态的情况下重新启动。该应用尚未在真实手机上运行过，
ARM（`arm64-v8a`）构建尚未验证。它不通过 Google Play 分发：其规则禁止加载
可执行代码的应用。

## 代理程序信任什么

| 对象 | 信任 |
|---|---|
| 发布密钥的 Ed25519 签名 | 信任。没有它，版本和任务列表都不会被接受 |
| 通道（HTTPS、镜像、GitHub 本身、Nostr 中继器、完整节点） | 在完整性上不信任：文件被替换会破坏签名或指纹，记录被替换会破坏其签名 |
| 任务内容 | 不信任：参数会被校验，工作量受限，任务中没有代码 |
| 本地模型的回答 | 不信任：这是文本，会作为未经验证的内容发布 |
| 首次安装 | 信任到 GitHub 的 HTTPS 通道。可以用 `selftest --online` 命令检查已安装的内容 |

**诚实的边界。** 发布密钥的持有者可以向所有已安装的代理程序下发程序。目前
密钥在项目维护者手中。这是 SkyNet 网络中不应存在的单一信任点：在目标项目中，
程序只会更新到其指纹由参与者在公共日志中投票接受的版本，仅有某人的密钥签名
是不够的（[CURRENT_DESIGN, 第 8 节](CURRENT_DESIGN.md)）。不想信任该密钥的
参与者可将 `update` 设为 `notify`，并在阅读变更后手动更新。

## 威胁表

| 威胁 | 如何防范 | 遗留问题 |
|---|---|---|
| 仓库或具有写权限的账户被攻破：替换代理程序 | 版本只有带仓库中不存在的密钥的签名才会被接受 | 在密钥被盗前已防范 |
| 在传输途中或在镜像上替换文件 | 版本说明的签名和每个文件的 SHA-256 | 已防范 |
| 回滚到旧的有漏洞版本 | 版本号必须大于当前版本 | 对已安装的代理程序已防范。新安装会取仓库中现存的内容 |
| 恶意任务 | 任务不携带代码；内核校验参数并限制工作量和内存；有时间上限 | 有限防范：已签名任务可能占用处理器直到时间上限 |
| 重放旧的已签名任务列表 | 列表编号不得小于已见过的编号；列表可以有有效期 | 有限防范：全新安装可能获得旧列表并无谓地计算已关闭的任务 |
| 损坏的版本 | 启动器在三次快速崩溃后，或新版本文件丢失时返回上一版本，并记住不可用的版本号。它会以不断加长的暂停执行重复的重启请求 | 对启动时的崩溃已防范。计算中的静默错误由结果比对捕获 |
| 发布密钥被盗 | 密钥存放在仓库之外，在 Windows 上按所有者账户加密 | **未防范。** 窃贼可以发布恶意版本。更换密钥要靠用旧密钥签名的新版本来完成，而窃贼也能拿到它 |
| 发布密钥丢失 | 所有者处有备份 | 没有密钥就无法更新已安装的代理程序：参与者将不得不重新安装代理程序 |
| 伪造结果 | 整数计算在不同 GitHub 账户之间比对；收集器把所有密钥合起来算作一票；发现的结果在汇总时重新计算 | 有限防范：一个人用两个账户可以“确认”他自己。没有奖励，因此这样做没有好处，但破坏者仍可能存在。维护者会抽查重算 |
| 来自他人账户和免费密钥的垃圾流 | 收集器只接受签名正确、指纹正确且任务已知的记录；节点限制大小、频率和总量 | **对密钥未防范**：密钥没有任何成本，因此垃圾可以无休止地发送。这是项目主要未解决问题的一部分 |
| 设备密钥泄露 | 密钥存放在代理程序文件夹中，且不发送到任何地方 | 复制了 `identity.key` 文件的人，就能以该设备的名义签名。纯 Python 实现的签名没有防范时序测量 |
| GitHub 令牌泄露（旧方式） | 代理程序不存储令牌，它从 `gh` 或环境变量获取令牌，并且除通过 HTTPS 发送到 GitHub 外不发送到任何地方，不带重定向 | 具有公共仓库写权限的令牌仍是参与者的责任 |
| 代理程序旁边的外来代码（当前文件夹中被塞入的模块） | Python 隔离模式（`-I`） | 已防范。对同一台电脑上以同一用户权限运行的程序没有防护 |
| 参与者资源消耗 | 默认一个进程、最低优先级、电池供电时暂停、时间上限、`pause` 和 `stop` 命令 | 电费由参与者自行无偿承担 |
| 维护者停止所有代理程序 | 版本说明中带签名的 `halt` 标记；在关闭更新时也生效 | 这是有意设置的杠杆：仅停止，不启动任何东西 |

## 代理程序会报告哪些自身信息

仅发布记录的内容：任务名称、分片编号、结果数字、计算耗时，以及（若未关闭）
类似 `linux-amd64-py3.12` 的粗略平台标签。请求发往 GitHub（任务和版本）以及
`trust.py` 中的中继器和节点（记录）。记录是公开的，并由设备的固定密钥签名，
因此同一台设备的结果可以相互关联，而接收方会看到发送方的网络地址。
不会收集参与者的文件、网络和设备信息。

## 维护者操作流程

发布密钥只创建一次，并存储在仓库之外：

```
python tools/keytool.py generate
```

所有者用命令 `python tools/keytool.py backup` 自行手动备份秘密，并将备份存储在
电脑之外。秘密不得展示给 AI 助手，也不得粘贴到聊天记录和文件中。

代理程序的新版本：

```
python tools/make_release.py --seq <下一个编号> --version <x.y.z>
```

然后把 `agent/` 中变更的文件上传到仓库。新的任务列表：

```
python tools/sign_tasks.py
```

然后上传 `tasks/index.json` 和 `tasks/index.json.sig`。从两个来源汇总结果
（签名记录和 GitHub 评论；`--net-only` 或 `--github-only` 只保留其一）：

```
python tools/collect_results.py
```

在修正错误之前停止所有代理程序的工作：发布带 `--halt-through <编号>` 和原因
的版本说明。

## 这里缺少什么，以及为何要如实说明

- **这不是分布式网络。** 任务和版本由一个仓库分发、由一个密钥签名。结果和
  任务看板上的任务已经通过多个相互独立的平台流转。[强制要求](../ru/REQUIREMENTS.md)
  中针对代理程序的 R1–R4 要求既不适用，也未被满足。
- **无法防范多个密钥和多个账户。** 对于无偿阶段，这是可以接受的；重要结果由
  重算确认。
- **Android 尚未在真实设备上验证**；macOS、Linux 和 Android 上的自动启动只在
  所创建文件的层面验证过。有两个情况根据文档作了处理，但也尚未在真实设备上
  验证：Windows 上来自 Microsoft Store 的 Python（它看到的是 `AppData` 和
  注册表的私有副本，因此代理程序文件夹位于用户配置文件夹中，自动启动需手动
  添加），以及 macOS 上来自 python.org 且未安装证书的 Python（代理程序会改用
  系统证书文件重试请求）。
- **首批任务很轻。** 整个第一批（702 个分片）在一台台式电脑上，以 16 个最低
  优先级的并发进程运行，共耗时 15.5 小时处理器时间，也就是按墙钟时间约一小时
  [2026 年 11 月 22 日在一台 PC 上测得]。该机制已准备好承接重型任务。结果如何：
  [results/FIRST_RUN.md](../../results/FIRST_RUN.md)。
