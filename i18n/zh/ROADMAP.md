# 路线图：防范作弊

[English](../../docs/ROADMAP.en.md) · **中文** · [Español](../es/ROADMAP.md) · [Français](../fr/ROADMAP.md) · [Deutsch](../de/ROADMAP.md) · [Italiano](../it/ROADMAP.md) · [Русский](../../docs/ROADMAP.md) · [Português](../pt/ROADMAP.md) · [العربية](../ar/ROADMAP.md)

状态截至 2026 年 11 月 23 日（在 v0.2.2 发布后更新）。这是一份**工作计划，而非对结果的承诺**。标记 `[x]`
表示“已完成，并且可以通过仓库或网络记录加以验证”；`[ ]` 表示“未完成”。带有 [计算]
标记的数字由公式得出，未经测量。本路线图会在每次状态变更时更新。

## 1. 目标与完成标志

**项目当前阶段的目标：**找到一种验证诚实性的方法，使以下强制性要求同时得到满足
（[REQUIREMENTS](REQUIREMENTS.md)）：

- 无法欺骗网络：欺骗无利可图或有损，即使对空账户新手、在合谋情况下以及在拥有大量密钥时
  也是如此；
- 不预先收取任何资金：没有押金、没有缴费、没有罚款；
- 参与有利可图，验证诚实性的成本低廉。验证额外开销的参考值：模型请求约为工作的 5%，训练
  约为 20%（尚未确认）。

**以下各项全部具备时，工作即视为完成：**

1. **已写明究竟保证什么**（决定 D1）：针对请求的结果、训练步骤、支付和历史；针对空账户、
   任意数量的密钥、退出以及任务验证者的完全合谋。该要求允许“欺骗无利可图”；不必证明
   每一次尝试都严格亏损。
2. **针对攻击表中的每一种攻击，已写明节点据以拒绝虚假申报的规则，以及它依据哪些数据这样
   做。**单独给出错误接受的概率、网络受到的损害，以及合谋群体相对于不作为和相对于诚实工作
   的净收益。对该规则的证伪示例：诚实情况与虚假情况中，节点看到的数据完全相同。抽样、小
   错误概率以及“存在诚实观察者”都作为假设写入。
3. **已算出验证的完整成本**，即相对于同一任务不经验证的情况：执行者和验证者的工作、内存、
   流量、存储、写入日志、争议、故障后的重试。已推导出在电费昂贵情况下资源充足参与者的净
   收入、设备较弱参与者的额外支出，以及没有设备的消费者的价格。账户余额为零也可以写入日志和发起争议；
   可能损失的只有尚未到期的奖励。
4. **计算可复现：**附有规则和内核的版本、输入、枚举边界、输出和哈希；计算已在第二台设备上
   重复。重复确认的是计算本身，而非模型本身的正确性：后者单独论证。
5. **无法通过推理确定的内容已测量：**不同显卡上结果的逐位一致、整数模型的速度和质量、争议
   的成本。配置、指标和阈值在测量之前就已确定。
6. **其余要求未被违反：**网络在缺少任意一个节点或平台时仍能运行，完全停机后仍能自行恢复，
   记账依据得以恢复；网络分裂时，有争议的支付等待共同的历史记录，重复不会被支付两次。

诚实的结果同样是一种结果：如果对某类任务而言廉价验证不可能实现，那就应当用证明来表明这一
点，并指明任务类别和验证者所依据的数据，而不是以“没有思路”来代替。

**关于防护强度的已知情况。**

- 方案 A，无合谋：在所枚举的族中（两波伪造，9200 万种策略），提交伪造结果后退出并不比普通退出
  收益更多 [计算]。
- 方案 A，合谋：提交伪造结果后退出开始有利可图的网格起点——在“进行中的工作不超过三分之一”规则
  下，合谋比例为 87.5%（任意规模的任务）和 89.0%（相同任务）；无此规则时为 80%。网格步长
  为 0.002–0.02；其他策略族尚未枚举 [计算，[FIRST_RUN](FIRST_RUN.md)]。
- 方案 B，无合谋：精确比较时，伪造得不到支付。
- 方案 B，合谋：`q` 是合谋群体在该模型验证者中所占的权重比例。只有在任务被选中且所有 `k`
  名验证者都参与合谋时，伪造才会得到支付。每提交一个伪造的平均支付为 `R·q^k`（`R` 为任务
  价格），且与 `p` 无关 [计算]。当 `q = 1` 时，这就是全部价格。对于空账户新手，无可扣除。
- 在验证者完全合谋情况下实现零虚假支付，对方案 A 和方案 B 都尚未得到证明。要实现这一点，
  需要对每个获得支付的结果，按任何节点都能自行验证的数据进行验证。完全重算会增加约 100%
  的工作量。试点测量：为模型的一行构建 RISC Zero 证明耗时 22 分 10 秒；在 zkVM 中执行八行
  的耗时约为常规方式的 17,700 倍，该耗时不包括生成证明。这些测量并未给出价格的一般下限。
- 方案 B 的收入波动：每月 6,000 个任务、每 100 个验证 1 个、成本为价格的 95% 时，出现亏损
  月份的概率为 33.10% [计算，FIRST_RUN]。
- 首次计算运行（702 份）在一台计算机上完成。到 11 月 23 日，第二台设备重算了全部 702 份，
  全部一致。其记录由密钥 `46000d30…` 签名，可在完整节点上获取。两台设备都属于维护者，
  因此这还不是来自独立参与者的确认。

**尚未解决的问题。**

1. 合谋中的空账户新手（方案 B）：每次尝试的平均收益为 `R·q^k`，没有损失。
2. “长期诚实，随后大规模欺骗并退出”：损失以待结算金额为限，收益随伪造数量增加而增长。
   针对方案 B 的修复方案已提出，但尚未计算。
3. 免费密钥带来的垃圾流量。生成密钥不需要花钱；用处理器工作来付费会让较弱设备处于更不利的地位。
4. 验证前就已被使用的结果。回答已被用户读取，步骤已进入训练；限制支付并不能弥补这一点。
   在方案 B 中，这同样适用于未被选中的任务。
5. 以发行积分来支付训练任务：由谁、按什么规则批准。正确完成但自行指派的任务不应产生积分。
6. 稀有模型：验证者圈子很小，对其而言 `q` 可能接近 1。
7. 数据的可用性，以及在不披露私密请求内容的情况下处理相关争议。
8. 整数模型的逐位一致仅在短输入上得到三台设备的确认；长上下文、速度和质量尚未测量。
9. 不求利益的破坏者，以及训练数据的投毒。经济防护对他们不起作用。

## 3. 决定

决定 D1–D5 已于 2026 年 11 月 23 日作出，D6–D25 于 2026 年 11 月 24 日作出（按所有者指示；D18–D25 针对阶段 4 的问题，论证见 [VERIFICATION_SEARCH](VERIFICATION_SEARCH.md) 第 6 节）。

| 编号 | 问题 | 决定 |
|---|---|---|
| D1 | 以什么作为保证 | **作弊者得不到他想要的结果。** 无法杜绝欺骗的尝试，但任何尝试对其发起者而言都必须是无用的：相对于诚实工作和相对于不作为，伪造的预期收益不大于零，对任何合谋群体都是如此，包括空账户新手和任意数量的密钥。目标是让虚假结果完全得不到支付。不要求每一次尝试都严格亏损。有限但为正的泄漏（例如方案 B 中新手的 `R·q^k`）**不满足**该标准，并仍是开放的漏洞 |
| D2 | 付费依据 | **已采纳：只对可验证的结果付费。** 已开启的设备、运行时间和申报的算力不构成付费依据：显卡也可以被无关的事务占满 |
| D3 | 方案 A 或方案 B | **在相同攻击和相同成本下比较之后（阶段 2）作出决定。**主要候选是方案 B |
| D4 | 不可变更的验证核心 | **已以强化形式采纳。** 验证自动进行，无需人工参与，也不经过投票。验证规则不因投票而改变。每个节点按照固定的规则指纹自行执行验证，因此即使某个节点或某个程序供应商替换了算法，也不会改变其他节点的决定。尚未解决：如何修复核心本身的错误（只能迁移到新网络），以及参与者如何确认自己的程序与公布的指纹一致（可复现构建）。当前为小型代理程序签名的发布密钥是研究工具；目标网络中不应存在它 |
| D5 | 整数 Qwen3.5-4B 的首次实验 | **已获批准：**维护者家用 Linux 上的 RTX 2060 显卡、他的电脑，以及经同意后通过小型代理程序接入的其他参与者的设备。在阶段 0 之后执行 |
| D6 | 损害是否属于 D1 | **是**（2026 年 11 月 24 日按所有者指示决定）。“作弊者得不到他想要的结果”不仅涉及积分，也涉及结果：虚假回答不得作为已验证结果交付给用户，虚假步骤不得进入模型。因此，结果只有在经过不依赖合谋比例的验证之后才能使用，否则必须明确标记为未验证 |
| D7 | 不依赖合谋比例的验证，还是削弱 D1 | **要求不依赖合谋比例的验证**（2026 年 11 月 24 日）。D1 不会削弱为“只要合谋者少于 q\*”。阶段 4 成为主要工作 |
| D8 | 从空账户发起争议 | **只有本任务通过抽签指定的验证者和用户本人可以就其请求发起争议**（2026 年 11 月 24 日）。无需押金；争议流量受验证和请求数量限制。其他人只能在任务板上报告可疑情况，无权停止支付 |
| D9 | 谁批准训练计划 | **没有任何个人：计划由固定规则从公开目录和考试结果推导出来**（2026 年 11 月 24 日）。不经过投票。积分只为计划中的任务发行，每个任务内容只计一次 |
| D10 | 交换时单方的泄漏 | **视为违反 D1。** 积分和其他价值的交换只能通过日志进行，双方作为一条记录，日志之外没有可信第三方 |
| D11 | 不可变更核心的构成 | **验证、“只支付已验证结果”规则、积分发行规则、争议和日志规则。** 费率、网络费用和模型目录只能在核心所固定的范围内变更 |
| D12 | 权重计时与验证窗口 | **网络的活跃时间**，而不是日历时间：网络停止时，权重不会老化，验证窗口也不推进 |
| D13 | 方案 B 中的任务准入 | **引入方案 A 的新手路径：**任务访问权限取决于密钥的待结算金额。方案 A 与方案 B 之间的最终选择（D3）在比较之后作出 |
| D14 | 争议成本 | **估算采用记录成本最低的二层网络。** 争议成本与可从败诉方扣除的金额之间的差额，由向消费者收取的网络费用支付，而不是通过发行积分支付 |
| D15 | 重复验证与学徒验证 | **可以复制的简单重算不支付报酬。** 只有当验证结果无法通过复制他人回答获得时，验证才获得报酬 |
| D16 | 诚实的硬件故障 | **不按作弊惩罚：**任务不支付，待结算金额不清零；每个密钥的此类故障次数有限 |
| D17 | 方案 B 中请求支付的来源 | **仅来自用户的付款**，不发行积分 |
| D18 | 以经证明的改进支付训练 | **作为训练付费的新单位候选进行研究，但尚未采纳。** 这既不是对步骤的验证，也不是无损害的证明：模型只按规则 D9 发布。是否采纳将在计算 M7、M8、M10–M12 和实验 O6（D5 之外，需所有者批准）之后决定。对步骤本身验证的探索仍在继续 |
| D19 | 微小密码学错误 | **作为明确假设予以允许**，但须满足三个条件：随机性来自最终固定之后的外部信标，抽样不由执行者的数据推导（不使用 Fiat–Shamir），已记录单次尝试成本的下界且 `ε·R` 小于它。每次尝试的错误不超过 `2⁻⁸⁰`。带 `q^k` 泄漏的普通抽样验证并不因此得到解决 |
| D20 | 外部信标 | **至少两个独立的公开来源**，取值在最终固定之后预先指定的时刻进行，且不得跳过。来源及影响它们的代价在阶段 2 选择；对它们的信任作为假设记录。在选定方案之前，不将其纳入抽样设计 |
| D21 | 谁验证模型回答 | **不依赖合谋的回答验证——只能由自行验证的付款方进行。** 网络不为未经检查的回答付费。没有设备的用户可以自行指定验证者；这是其自身的假设，网络不为其承诺 D1。对此类用户的保证仍是未决问题 |
| D22 | 为廉价验证而改变产品 | **允许作为计划中具有明确契约的单独任务类型**（规范的 token 选择、整数配置、结果可验证的任务、精确优化器），在实验 O5 和计算 M17 之后。普通抽样仍保留“未验证”标记 |
| D23 | 付款方的虚假争议 | **先进行计算 M9。** 在选定无需押金限制虚假争议的规则之前，不启用付款方验证 |
| D24 | 日志中的回答密文 | **是：**与验收一起作为一条记录写入，每个回答约 2–4 KB |
| D25 | D1 的双向表述 | **不变：**比诚实工作更差、但比不作为更有利可图的伪造，同样违反 D1 |

**工作顺序。**首先完成阶段 0——小型代理程序和智能手机应用，以便其他人也能参与工作。然后
按本路线图进行阶段 1–5。

## 4. 阶段与检查清单

阶段 0 首先完成。然后阶段 1–4 并行进行：它们是计算和推理。阶段 5（实验已由决定 D5 批准）
在阶段 0 之后进行。阶段 6 汇总结果。

### 阶段 0. 小型代理程序和智能手机应用（首先完成）

**阶段目标。**在每个受支持的平台上，用户走完“下载 → 安装 → 运行”的路径，之后小型代理
程序无需人工参与即可自行更新、领取任务并提交结果。无需账户，无需管理员权限，无需预先
安装 Python。每一步都在真实设备上验证过，而不仅仅是通过自动测试。

**完成条件：**对于下列列表中的每个平台：没有经验的人仅凭一页说明就走完整个路径；该设备上
的代理程序自行获取了新版本，自行领取了新任务列表中的任务，其结果出现在完整节点上并与
另一台设备的结果一致。已记录系统、架构、更新前后的版本以及节点上的记录标识符。

平台：Windows、Linux、Android（2026 年 11 月 23 日的决定）。不为 macOS 和 iOS 制作、也不
验证小型代理程序。Linux 的安装命令也许能在 macOS 上运行，但不受支持。Windows 版本以无代码
签名的方式发布：安装时 Windows 会显示 SmartScreen 警告，需要手动确认；文件的真实性通过
公布的哈希和项目签名加以验证。

已完成：

- [x] 公开仓库，九种语言的不可变更基础（标记 `core-v1`）。
- [x] 面向 Windows 和 Linux 的代理程序：经过签名的任务和更新，CI 中的自动检查
      （版本 0.2.0）。在终端中用一条命令安装；需要 Python 3.9+。
- [x] 无需账户即可访问的结果和[任务板](BOARD.md)。
- [x] 首个完整节点，保存记录历史。
- [x] 任务板上的首个研究任务“防范欺诈者”，以九种语言发布。
- [x] Android 试用应用 0.1.0（仅在模拟器上验证过）。

**步骤 1. 更新的可靠性（版本 0.2.1，不含新任务）**

- [x] 首次安装会用内置于安装程序本身的密钥校验发布版本的签名，且校验发生在运行下载的
      代码**之前**（以前下载的代理程序会自我校验）。
- [x] 以单次原子操作切换到新版本：先准备好并校验新目录，然后只更换一个指针；上一个完好
      的套装会被保留。

### 阶段 3. 封堵已知漏洞

- [ ] **空账户新手。**候选方案：新手的首批任务是这样的——任何节点都能自行精确验证这些任务，只有
      在此之后才计入奖励和权重。备用方案：每个纪元的学徒支付总预算；它限制了泄漏，但无法使
      其归零，而且合谋可能占满所有名额。
- [ ] **“长期诚实，随后大规模欺骗”。**候选方案：对密钥所有未结义务的总和设定上限，按最大
      可能收益计算。该上限只约束单轮攻击的收益，而非零泄漏。
- [ ] **免费密钥产生的垃圾。**候选方案：节点只接受已授权任务编号的数据，并限制大小、队列和
      每个纪元的工作量。信道仍然可以被填满；在任意数量的密钥下，尚未获得保证诚实新手有位子
      的方案。
- [ ] **验证前就已被使用的结果。**候选方案：在交付前验证回答块；将训练步骤保存在单独的分支
      中，只推进经过验证的后继。代价：延迟和内存。
- [ ] 训练任务：无需拥有特殊权限的参与者即可批准的规则。
- [ ] 稀有模型：由权重分布推导出的阈值，低于该阈值时网络不为该模型付费。
- [ ] 懒惰的验证者以及已知结果的重复提交：带揭示的隐藏承诺，按内容一次性记入。
- [ ] 诚实参与者的设备故障：不给作弊者带来收益的规则。
- [ ] 数据的可用性，以及在不披露私密请求内容的情况下处理相关争议。
- [ ] 网络停机期间的争议窗口、对过期历史的防护、网络分裂。

### 阶段 4. 寻找不依赖合谋比例的保证

寻找一种每个节点都能自行执行的验证，使得验证者之间是否一致无关紧要。这些研究方向尚未获批。对每个
方向都需要说明要验证的操作、数据、错误概率，以及整个请求或步骤的成本；然后要么推进到构造，
要么用反例排除该研究方向。

- [x] 模型委员会（六项研究与三项批评）分析了所有方向；结果和给小型代理程序的任务见
      [VERIFICATION_SEARCH](VERIFICATION_SEARCH.md)，2026 年 11 月 24 日。
- [x] 面向小型代理程序的首批精确计算：汇总第 5.3 节中的 M8、M10、M12 和 M14

      的计算推迟：现有工作中缺少能够明确界定这些计算的规则。
- [ ] **能以低成本精确判定结果是否正确的任务。**示例：对于岭回归，节点一次遍历数据即可验证最优性
      条件。问题：网络工作中有多大比例属于此类任务。应从这个方向开始：它能带来零虚假支付。 *结果：*仅在狭窄的任务类别中成立，此类工作的比例未知。
- [x] **用随机向量验证每一次矩阵乘法**，以代替重算。向量在结果固定之后选取；漏检错误的
      概率与合谋无关。对大 batch 有利；逐 token 生成时没有收益。其余操作（舍入、激活、缓存、
      优化器）需要单独验证。 *结果：*作为由网络节点执行的廉价验证已被否定（瓶颈在于流量）；作为由具有快速通道的付款方执行的验证仍然成立。

- [x] **不变层的精确部分和表：**节点由权重一次性推导出表格，之后通过读取和加法得到层的

- [x] **获胜 token 的证书**，用于大词表：执行者按组提交词表覆盖，节点检查上界，并且只在上界
      无法区分获胜者时才下探到各个 token。最坏情况下需要检查整个词表。 *结果：*作为贪心选择验证的一部分仍然成立。
- [x] **训练步骤作为精确的更新公式：**节点保存和验证的不是新的权重矩阵，而是更新因子。目前

- [x] **在窗口期内向任何参与者开放的争议。**保证是有条件的：需要至少一个获得了数据并来得及
      提出异议的观察者。空账户情况下由谁支付观察费用，尚未解决。留作备用。 *结果：*作为不依赖合谋的验证被否定。

## 5. 工作如何进行

1. 检查清单条目转化为任务：计算型任务（由小型代理程序计算，结果按一致性核对）或研究型任务
   （发布到任务板上）。
2. 参与者及其 AI 助手提交报告。报告只有在可验证时才会被接受：通过重算、证伪示例或来源
   引用。同意密钥的数量不能证明任何东西；任务板上任务作者的决定也不能确认计算。
3. 根据验证结果，任务被关闭、细化或产生新任务。
4. 状态变更以一次修改（附日期）写入本路线图和 CURRENT_DESIGN。
